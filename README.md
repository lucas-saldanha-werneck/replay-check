# replay-check

Independent demo, not affiliated with CI&T (cliente não diz). All data in `examples/` is invented.

When a legacy platform is rebuilt as event-driven services, two things tend to go wrong: events get delivered twice, and the new numbers drift from the old ones. `replay-check` is a small Python tool (standard library only) that checks both on a stream of ledger events.

It takes a JSONL file of events (`event_id`, `account`, `type`, `amount`, optional `ts`) and:

- folds them into balances using `Decimal`, skipping any `event_id` it has already seen;
- reports repeated ids whose payload differs (a conflict, first one wins) and malformed events;
- replays the stream in random order several times and checks the balances do not change;
- shows which accounts a naive, non-idempotent replay would get wrong;
- optionally compares the result with a legacy balance export (CSV `account,balance`), with a tolerance.

The exit code is 0 on PASS and 1 on FAIL, so it can run in CI against a historical export.

## Run

```
python -m replay_check examples/events.jsonl --legacy examples/legacy_balances.csv
```

Options: `--shuffles N` (default 20), `--tolerance 0.01`. Requires Python 3.9+. For the tests: `pip install pytest && python -m pytest -q`.

## Example result

The bundled example has 43 invented events, 3 of them retried deliveries. The invented "legacy" export counts every delivery, so the check fails on 2 of 4 accounts (ACC-001 by 620.78 and ACC-004 by 451.77). Those are the two accounts that received a retried event. Balances stay the same across 20 shuffled replays.

## What was tested

- 13 offline pytest tests, run in GitHub Actions: Decimal sums, duplicate skipping, conflicting payloads, invalid events, out-of-order counting, order independence with duplicates, diff tolerance and missing accounts, report PASS and FAIL, CLI exit codes, and the expected findings on the example data.
- The example numbers above come from running the tool locally and in CI.

## What was not tested

- Real data of any kind. The events and the legacy file are made up, and the legacy file is generated by a script that double-counts retries on purpose.
- Large files. The tool reads the whole file into memory.
- Rules that depend on order, such as overdraft limits or currency conversion. Balances here are plain sums, so the shuffle check is easy to pass.
- Event sources such as SQS, EventBridge or SFTP drops. The tool reads a local file only.
- Python versions other than 3.12 in CI (3.15 locally).
